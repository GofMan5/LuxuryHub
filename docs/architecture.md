# Архитектура LuxuryHub

Документ фиксирует каркас: что уже есть в репозитории, как части соединяются и в
каком порядке наращивать функциональность. Это не спецификация продукта —
доменная логика появится вместе с первыми фичами.

## 1. Контекст

```text
┌─────────────────────────────┐        ┌──────────────────────────────┐
│  LuxuryHub Desktop (Windows)│        │  LuxuryHub Backend (Go)      │
│  Rust + GPUI-CE             │◄──────►│  HTTP/JSON сейчас, gRPC потом│
│  нативное окно, свой UI     │  сеть  │  один бинарник, режимы       │
└─────────────────────────────┘        └───────────────┬──────────────┘
                                                       │
                                        ┌──────────────▼──────────────┐
                                        │ PostgreSQL (план)            │
                                        │ S3-совместимое хранилище     │
                                        │ (план, только под медиа)     │
                                        └──────────────────────────────┘
```

Клиент — единственный потребитель API на старте. Публичного веба нет, поэтому
первый транспорт — обычный HTTP/JSON: его видно в логах и `curl`, и он не требует
кодогенерации. Переход на gRPC/protobuf оправдан, когда появится второй клиент
или понадобятся стримы (см. §5).

## 2. Бэкенд: слои

```text
cmd/luxuryhubd        точка входа: env, лог, сигналы, запуск сервера
        │
internal/server      транспорт: маршруты, middleware, коды ответов
        │
internal/<module>/app          сценарии: оркестрация, транзакции, права
internal/<module>/domain       типы и правила: инварианты, FSM, деньги
        │
internal/<module>/adapters     Postgres, внешние API, кэш
```

Правило зависимостей: **внутрь**. `domain` не знает ни про `net/http`, ни про
SQL; транспорт не содержит бизнес-правил; адаптеры реализуют порты, объявленные
доменом или сервисом.

Пока в репозитории есть только `cmd` и `internal/server` — этого достаточно,
чтобы поднять процесс, проверить здоровье и подключить первые модули без
переписывания.

## 3. Клиент: слои

```text
lh-app     окно, навигация, сборка экранов, глобальное состояние
lh-ui      токены темы и переиспользуемые элементы (кнопки, карточки, списки)
lh-core    (план) доменные типы, команды, состояние экранов
lh-api     (план) HTTP-клиент, кэш на SQLite, авторизация, realtime
```

Правило: **никакого ввода-вывода в UI**. Сеть и диск живут в отдельных задачах,
результат приходит в состояние экрана и вызывает перерисовку. GPUI однопоточный
и рисует немедленно, поэтому блокирующая работа в `render` — ошибка, а не стиль.

## 4. Поток одного действия

1. Пользователь нажимает кнопку → экран формирует команду.
2. Команда уходит в задачу Tokio (сеть, диск) и не блокирует кадр.
3. Ответ парсится в доменный тип, ошибка маппится в понятное состояние экрана.
4. Состояние обновляется, GPUI перерисовывает затронутые элементы.
5. Для списков — виртуализация: рисуются только видимые строки.

## 5. Решения

| # | Решение | Почему | Когда пересматривать |
|---|---|---|---|
| 1 | Go без веб-фреймворка | stdlib `net/http` покрывает маршруты и middleware; меньше зависимостей — быстрее правки | при появлении сложной валидации и OpenAPI |
| 2 | HTTP/JSON на старте | видно в логах, не нужна кодогенерация, один клиент | второй клиент или стримы → gRPC |
| 3 | Один бинарник, режимы `api`/`worker`/`migrate` | деплой и локальный запуск одинаковы | разделение по нагрузке |
| 4 | Деньги — `int64` в минорных единицах | нет ошибок округления; валюта рядом с суммой | никогда |
| 5 | Клиент нативный, GPUI-CE | быстрый рендер, полный контроль над интерфейсом, Rust без GC-пауз | если нужен веб — отдельный клиент, не замена |
| 6 | Кэш клиента на SQLite | офлайн-просмотр и мгновенные переходы | объём данных/синхронизация |

## 6. План по фазам

**Фаза 1 — каркас (сделано).** Собирается бэкенд с `/healthz` и `/version`;
собирается клиент с окном и навигацией; есть Makefile и документация.

**Фаза 2 — первый вертикальный срез.** Один домен (например, каталог лотов):
таблица в Postgres, репозиторий, сервис, `GET /v1/items`, экран списка в клиенте,
загрузка через `lh-api`, состояния «загрузка/пусто/ошибка».

**Фаза 3 — деньги и сделки.** Оффер, сделка, эскроу-состояния, идемпотентность
запросов, журнал операций. Здесь появляется `domain`-слой в полном виде.

**Фаза 4 — контракт и стримы.** Protobuf-схема в `api/`, gRPC-сервер рядом с
HTTP-фасадом, server-streaming для обновлений, кэш и ресинхронизация в клиенте.

## 7. Чего сознательно нет

- микросервисов и брокера сообщений — один процесс дешевле в разработке;
- ORM — запросы пишутся явно, схема под контролем миграций;
- GraphQL — один клиент, фиксированные экраны;
- своей платёжной интеграции на старте — эскроу вводится на фазе 3.
